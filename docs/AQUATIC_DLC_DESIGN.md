## 第一部分　理念

### 1.1 设计宪法（实现与评审都以此为准）

| # | 原则 | 含义 | 反例（现在的做法） |
|---|---|---|---|
| P1 | **能力决定动作** | 一只油库里能做什么、做成什么样，只由它的身体能力和真实环境决定 | 按场景写跳跃曲线，导致有的高跳、有的平移 |
| P2 | **一个能力只写一次** | 跳、走、游、爬、推、叼、搬、划各只有一个实现，全部行为复用 | 上船、登岸、自救、救援各写一套移动 |
| P3 | **行为只说目标** | 行为层只声明“要去哪、要把什么弄到哪”，不决定怎么动 | 行为里直接 `setPos`、选曲线、定时长 |
| P4 | **限制必须附带手段** | 新增任何限制，都要同时让规划器有办法满足它；做不到时先换办法 | 加上 `hop_exceeds_body` 后原样重试 14 次 |
| P5 | **世界是连续的** | 位置、空间、拥挤由几何和碰撞产生，不查座位表、不查冲突矩阵 | 102 个离线座位与 8×8 冲突表 |
| P6 | **物理是唯一真相** | 在不在船上、在不在窝里、成没成功，看实际位置和接触，不看标记和租约 | 放下失败后孩子又被当回乘员 |
| P7 | **帽船是会漂的小陆地** | 帽船对油库里来说只是一块会动、会倾斜、会翻的地形 | 登船、下船、入座、乘员各有专门流程 |
| P8 | **真实失败有后果** | 所有办法用尽才失败；失败要留下现场并产生后果，不瞬移，不伪成功 | 原地搬运被记为成功 |
| P9 | **扩展只经接口** | 水生 DLC 只通过底座的扩展点接入，底座代码不认识 DLC | 底座里散落 `if aquatic` |
| P10 | **先验能力，再验行为** | 技能在能力展厅单独验收，行为出问题先定位是哪个技能 | 每次只能在完整场景里猜问题在哪 |
| P11 | **真实驱动，调欲望不写死**（用户裁决） | 行为来自多种欲望和需求的真实竞争；想要某种演出，就调整欲望强度或优先级，不硬编码顺序和门槛 | “先载幼体、船长最后上船”写成硬性阶段；用固定流程保证演出 |

### 1.2 底座与 DLC 的关系

```
┌───────────────────────── 水生魔理沙 DLC ─────────────────────────┐
│ 物种能力修正 · 帽子四形态 · 浮动地形（帽船）· 水中技能 · 水上需求   │
│ 水上家庭规则 · 落水事件 · 帽船演出 · 水上场景与展厅               │
└──────────────── 只通过扩展点接入 ↓（底座不引用 DLC）────────────────┘
┌──────────────────────────── 油库里底座 ───────────────────────────┐
│ 身体 Body · 能力表 Ability · 物理 Physics · 地形 Terrain · 容器 Container │
│ 技能 Skill · 规划 Planner · 意图 Intent · 需求 Need · 归属 Custody      │
│ 演出 Presentation · 日志 Trace · 能力展厅                               │
└───────────────────────────────────────────────────────────────────┘
```

- **底座的受益者不止水生种**：陆地接生、入窝、赤油取食、迁徙、捕食者落地都用同一套底座，E11 的陆地问题在底座阶段就能修好。
- **检验标准**：把 DLC 的注册全部关掉，底座和陆地玩法照常编译、运行；打开后，水生内容只在“会漂的地形”和“水中技能”上叠加，不改动底座的任何判断。

## 第二部分　底座设计

### 2.1 概念词典

| 概念 | 定义 | 拥有的数据 | 不允许做的事 |
|---|---|---|---|
| **Body** 身体 | 一只油库里的物理存在：位置、速度、朝向、足迹、质量、支撑面 | 物理状态（不存档的部分每 tick 重算） | 被物理层以外的代码直接改位置、速度、朝向 |
| **Ability** 能力 | 由体型、阶段、体力、伤病、负重、物种算出的上限集合 | 不存档，每次查询时计算；系数来自数据文件 | 被行为代码临时加减 |
| **Terrain** 地形 | 能站、能走、能跳上去的表面：静态方块，或会动的地形 | 碰撞形状、支撑面、坡度、是否在动 | 区分“乘客”和“行人” |
| **Container** 容器 | 有“里面”的地形：窝、接生帽、帽船帽腔、房屋、地洞 | 内底面、边沿、容量（由几何决定） | 用标记代替几何判断“在里面” |
| **Skill** 技能 | 一种身体动作：走、跳、游、爬、推、叼、搬、划、转向、站稳 | 当前执行状态和进度值 | 绕过能力表；直接写位置 |
| **Intent** 意图 | 行为想达成的结果：去某处、把某物弄到某处、扶正、休息 | 目标、成功条件、来源、紧迫度 | 指定使用哪个技能 |
| **Planner** 规划 | 把意图拆成技能序列，失败就换手段 | 本轮候选手段、看门狗记录 | 原样重试 |
| **Need** 需求 | 长期存在、按紧迫度产生意图的驱动：饿、困、冷、想回窝、帽子不在身边 | 需求值（沿用现有组件） | 直接执行动作 |
| **Custody** 归属 | 某物属于谁、现在在哪个形态 | 主人、形态、位置 | 由动作各自维护副本 |
| **Presentation** 演出 | 动画与表情 | 无业务数据 | 从行为和标记推导动作，而不看技能与物理状态 |

### 2.2 子系统设计表

| 子系统 | 职责 | 输入 | 输出 | 取代的现有部分 |
|---|---|---|---|---|
| **物理层** | 每 tick 移动身体与动态地形：重力、浮力、碰撞、推挤、平台携带 | 技能施加的速度与力 | 新位置与接触信息 | 散落各处的 `setPos`、冲量与速度清零 |
| **能力表** | 回答“这只现在能跳多高、多远、能搬多重……” | 体型、阶段、体力、伤病、负重、物种修正 | 能力值 | `YukkuriLocomotion.limits`、`CrewReach`、`canJump` 二值判断、`hat_vessel.json` 中的跳跃参数 |
| **地形层** | 统一表示静态与会动的地形，提供碰撞、支撑面与坡度 | 方块世界，以及已注册的动态地形 | 碰撞形状、支撑面、坡度 | 帽内座位表与“乘客”钉位 |
| **容器判定** | `Occupancy.of(body, container)`，给出 `INSIDE_SUPPORTED`（在里面且站稳）、`ON_RIM`（在边沿上）、`PARTIAL`（只进去一部分）、`OUTSIDE`（在外面）四种结果 | 身体足迹、容器内底面 | 四种结果之一 | 9 处各写一套的窝、帽、屋判定 |
| **技能层** | 执行一个动作并报告进度和动画 | 意图拆出的一步、能力、地形 | 施力、进度、动画 | 各行为里写死的动作 |
| **规划层** | 把意图拆成技能，按代价选手段，看门狗换手段 | 意图、能力、地形与容器 | 技能序列、失败原因清单 | 各行为的前置判断、重试循环、失败预算 |
| **需求层** | 长期需求按紧迫度产生意图 | 现有需求组件 | 意图 | 行为里的“顺便处理一下”（例如事后找帽子） |
| **归属层** | 物品（帽子、木棍、食物）的形态与主人 | 物理事实 | 归属事件，并驱动需求 | 各动作自行找回帽子的代码 |
| **演出层** | 由当前技能与物理状态选择动画和表情 | 技能状态、物理状态、情绪 | 同步给客户端的姿态与表情 | 多处推导的表情与动作选择 |
| **日志层** | 统一前缀记录意图、规划、技能和物理事件 | 各层事件 | `[intent]` `[plan]` `[skill]` `[body]` | 各模块自定的诊断行 |

### 2.3 能力表设计

| 能力 | 用途 | 推导（形式，系数待展厅定稿） |
|---|---|---|
| `hopHeight` | 一次蹦跶能抬升的最大高度 | 体型 × 阶段 × 体力系数 × 伤病系数 |
| `hopReach` | 平地一跳的最远水平距离 | 与 `hopHeight` 同源 |
| `walkSpeed` | 行走速度 | 体型 × 阶段 × 体力 × 负重 |
| `stepUp` | 不用跳、直接走上去的最大台阶高 | 体型比例；高于此值就要 Hop |
| `swimSpeed` | 水中前进速度（底座中为挣扎式前进，很弱） | 体型 × 体力；物种可修正 |
| `climbRise` | 扒住边沿后能爬上去的最大高差 | 体型 × 抓握 |
| `grip` | 在坡上、攀爬中、扶帽时不打滑的能力 | 体力 × 伤病 |
| 搬运（不设数值） | 能否叼起或托起 | 不设质量数值：被搬者体型小于搬运者即可搬起，被搬者越大搬得越慢、越容易滑落（用户裁决：不必细到重量） |
| `reach` | 嘴或辫子能够到的距离 | 体型；魔理沙的辫子另加 |
| `pushForce` | 推物体的力 | 体型 × 体力 |
| `endurance` | 持续动作消耗与恢复 | 沿用现有体力系统 |

- **成体基准（用户裁决）**：成体蹦跶最高 **0.8 格**，最远 **1.0 格**。子油、赤油按体型、体力、伤病比例缩小，系数在能力展厅中调整。
- **单一来源**：所有技能和规划只读这张表。现有 `YukkuriLocomotion` 的公式（`S`、`F`、`L`）作为第一版系数迁入，不另造公式。
- **物种修正**：只能乘以系数或增加能力项，比如魔理沙的辫子增加 `reach` 和托举。DLC 的修正也通过这个口子接入。

### 2.4 技能目录

| 技能 | 可行性检查（读能力和几何） | 执行方式（只施力） | 动画来源 | 失败回报给规划器 | 复用者 |
|---|---|---|---|---|---|
| **Walk** | 有路径；坡度与台阶在能力内 | 沿路径施加速度 | 行走或蹦跳步态 | `NoPath(最近点)` | 所有移动 |
| **Hop** | 在能力内求**最低**可行弧线 | 一次起跳速度，之后交给物理 | 起跳、腾空、落地，由速度决定 | `TooFar(差多少)`、`TooHigh(差多少)`、`Blocked(什么挡着)` | 上下船、跨缝、上台阶、入窝 |
| **Swim** | 身在水中；体力在 | 限速推进 | 水中挣扎前进（游泳动作在美术待办里） | `Exhausted`、`Current(水流太急)` | 落水、自救、找帽 |
| **Climb** | 边沿在 `climbRise` 内；抓得住 | 分段上拉，时长不短于动画 | 扒檐、上拉 | `Slip(打滑)`、`TooHigh` | 落水上船、上岸 |
| **Push** | 接触到物体 | 对物体施力 | 顶推 | `TooHeavy`、`Stuck` | 推帽船、推食物、扶正 |
| **Grab** | 目标在 `reach` 内，且体型小于搬运者 | 建立口或辫子的接触约束 | 叼、辫子卷起 | `TooFar`、`TooHeavy` | 搬孩子、搬食物、捡帽子 |
| **Carry** | 已抓住 | 搬运者移动，被搬者受接触约束 | 叼着走、辫子托着走、被托着 | `Dropped(掉了，落在实际位置)` | 救援、接生收尾、搬家 |
| **Release** | 落点可支撑 | 解除约束，被搬者交给物理 | 放下 | 无：放下就是放下 | 同上 |
| **Paddle** | 有可用的划桨物（叼着的或帽内储物里的） | 对所站的帽船施力和转向力矩 | 划桨 | `NoPaddle`、`Exhausted` | 航行、靠岸、转船去够人 |
| **Face** | 无 | 转身速度受能力限制 | 转身 | 无 | 所有需要朝向的动作 |
| **Hold** | 无 | 站稳，抵抗坡度 | 站稳或抓住 | `Slip` | 帽船倾斜、等待 |

技能是可以组合的“乐高”：救援是 Swim/Paddle + Grab + Carry + Release；扶正是 Swim + Push；登船是 Walk + Hop。

### 2.5 规划层设计

**意图类型**

| 意图 | 成功条件（物理事实） |
|---|---|
| `GetTo(place)` | 身体在目标附近并站稳；如果目标在容器里，要求 `INSIDE_SUPPORTED` |
| `Fetch(obj, place)` | 物体实际处于目标位置或容器里 |
| `Reach(target)` | 嘴或辫子实际接触到目标 |
| `Right(hat)` | 帽子实际帽口朝上并浮着 |
| `Rest(container)` | 身体 `INSIDE_SUPPORTED` 并进入休息状态 |
| `Hold()` | 站稳到指定时刻或指定事件 |

**手段**
- 规划器在一张“导航图”上搜索：节点是地面、帽内、水中的可站位置，边是技能。
- 代价 = 时间 + 体力 + 风险（水、危险、坡度）。
- 可行性来自技能的 `feasible`，返回差额（例如还差 0.4 格），规划器据此生成“先缩小差额”的前置步骤。

**手段库**（按代价从低到高自动选择，不写死顺序）
- 自己走近或绕路；
- 换个落点或边沿；
- 等待移动地形靠近（例如帽船正在靠岸）；
- 让地形移动（自己划船，或请船长划船）；
- 下水游过去，再扒上来；
- 推开阻挡物；
- 请他人代劳：搬运、救援，按关系和性格决定对方是否答应；
- 等待环境变化（水流把目标带近、天亮）。

**看门狗**
- 每个技能都要报告一个可度量的进度（距离、角度、高差）。
- 连续几次评估都没有进展，就把这个手段标为本轮不可用，换下一个。
- 同一手段在环境没有变化时不许再选。

**失败与后果**

| 状态 | 含义 | 去向 |
|---|---|---|
| `Progressing` | 有进展 | 继续 |
| `Blocked(原因, 差额)` | 当前手段卡住 | 规划器换手段 |
| `Exhausted(原因清单)` | 所有手段都不可行 | 交给行为的后果规则：呼救、哭、放弃、悲伤、溺水等 |
| `Interrupted(更高意图)` | 被更紧急的意图打断 | 当前结果按物理事实保留，不回滚 |

### 2.6 动作所有权与打断

- 一只身体同一时刻只执行一个技能，由规划器派发。
- 行为之间的抢占发生在“意图”层：比如危险意图打断照料意图。规划器收到新意图后，在技能的安全接缝处切换，不在半空中改动作。
- 被打断的意图不自动恢复。如果需求还在，会重新产生意图。

### 2.6b 驱动模型：演出由欲望竞争产生（P11）

- **欲望**：每只油库里同时有多种欲望，例如饥饿、困倦、寒冷、护幼、亲近、好奇、恐惧、想回水上、帽子不在身边、想玩。每个欲望有强度（来自现有需求、性格和环境）和权重（数据文件可调）。
- **选择**：每次评估时，取“欲望强度 × 权重 − 规划代价”最高的意图执行。高欲望可以在技能安全接缝处抢占。
- **想要的演出靠调参得到，不靠写死**：

| 想要的演出 | 做法 |
|---|---|
| 亲油通常先把孩子送上船，自己最后上 | 护幼欲望在“孩子不在身边”时很高，所以出航前它会先去满足这一项 |
| 下雨时不出航 | 寒冷与躲雨欲望压过“想在水上生活” |
| 孩子落水时亲油立刻去救 | 护幼加恐惧的强度远高于日常欲望 |
| 夜里在岸凹停泊 | 困倦加安全欲望选中能卡住船的地点 |

- **硬性规则只留给设定事实**，例如生殖只在岸上、水生只与水生配对、水伤数值。行为顺序、时机、“谁先谁后”一律由欲望竞争产生。
- **调参工具**：读数命令显示个体当前欲望强度与得分排名，`[intent]` 日志记录选择时前三名的得分，方便知道为什么选了这个。

### 2.6c 与现有 Goal 系统的接入

- 现状：`entity/YukkuriGoals` 注册了约 52 个按优先级排列的 vanilla Goal，陆地各模块都依赖它。不推倒重来。
- 新增**一个** `DriveGoal`，占用 MOVE / LOOK / JUMP 旗标。它内部做欲望竞争，执行选中的意图。已迁移的行为（先是水生和出生收尾）只作为意图注册到它里面，不再各占一个 Goal。
- 未迁移的旧 Goal 照常运行。vanilla 的优先级在注册时固定，所以 `DriveGoal` 只注册**一次**，放在最高优先级，用 `canUse` 决定要不要占用身体：
  - 只有选中意图的得分高于“旧系统需求估值”时才占用。估值由饥饿、困倦、恐惧等现有需求值换算，旧 Goal 所服务的需求也在欲望层里有一份读数。
  - 占用与让出都带滞回（得分要超过对方一定幅度、至少持续若干 tick），避免来回切换。
  - **不能**像 `AfloatAgenda` 那样把同一套逻辑注册成两个不同优先级的 Goal，那正是“一卡一卡”的来源。
- 这样新旧系统通过同一个 vanilla 仲裁共存，互不改写。
- `STATUS_HUB` 的反应仲裁保持不变，它作为“反应”输入欲望层，不直接动身体。
- 迁移完成的标志：某个模块的旧 Goal 从 `YukkuriGoals` 中删除，它的行为全部以意图形式存在。

### 2.6d 导航：分坐标系的统一规划

- 陆地用现有 `PathNavigation`；帽内用帽面高度场上的小网格寻路（帽局部坐标，不受帽子漂动影响）；水中用直线加避障。
- 三者之间的“过渡边”就是技能：岸 → 帽是 Hop，水 → 帽是 Climb，帽 → 水是 Hop 或跌落。规划时用当前帽子位置估算过渡边；帽子漂动后，在下一次评估中自动重估，不预先锁死。
- 目标在帽上的意图以“帽 ID + 局部坐标”表示，因此帽子移动时目标自然跟着走。

### 2.6e 数据驱动与热重载（让调参不用等 CI）

- 能力系数、欲望权重、技能参数（弧线余量、看门狗阈值）都放在数据包 JSON 中，注册 reload 监听，用 `/reload` 即时生效，不需要重新编译。
- 目前仓库还没有 reload 监听，M0 补上。
- `[skill]`、`[intent]` 日志带当前参数文件的短指纹，排查时能对上是哪一版参数。
- 用户在能力展厅里调手感：改 JSON → `/reload` → 重按展台。只有逻辑改动才需要 CI 出新运行包。

### 2.6f 同步、存档与区块

- **同步**：站在帽上的身体按“帽 ID + 局部坐标”同步；客户端用插值后的帽子姿态合成世界位置，帽和身体同帧移动，不会各自插值而抖动。
- **存档**：帽子保存站在它上面的身体 UUID 与局部坐标；读档后两者都加载了才重新关联。帽子没加载时，身体保持世界坐标，交给物理（可能落水），不凭空瞬移。
- **区块**：帽子漂到未加载区块时与 vanilla 实体一样停住；站在上面的身体随之停住。不为此另做补偿。

### 2.6g 性能预算

- 规划评估每 10 tick 一次，按实体 ID 错开；每轮最多评估若干个候选手段，可行性结果按“地形版本号”缓存。帽面高度场查询是常数时间。
- 物理层只为附近有玩家的实体做精细碰撞，远处实体沿用 vanilla 的简化移动。
- 日志的逐 tick 采样只在详尽开关下开启。

### 2.6h 调试显示

- 开关 `/yukkuri debug intent`：在个体头顶显示当前意图、执行中的技能、前三名欲望及得分。客户端只显示服务端同步来的文字，不推导。
- 帽面高度场有离线预览（`.local/previews/hull-heightfield/`），游戏内可选用调试粒子描出帽面轮廓。
- 用户试玩时一眼能看出“它想干什么、为什么卡住”，减少靠猜。

### 2.7 演出原则

- 动画是**运动的结果**：起跳、腾空、落地、扒檐、划桨、被托着，都由当前技能和物理状态决定，所以动画永远和动作一致。
- 表情的优先级只有一处：操作姿态 > 反应 > 伤病或哭泣 > 情绪 > 兜底。归属变化（比如帽子被拿走）通过情绪层产生持续表情，不靠一帧的反应。
- 客户端只播放同步来的姿态和表情，不自己推导。

## 第三部分　水生魔理沙 DLC 设计

### 3.1 DLC 只做四件事

| 类别 | DLC 提供的内容 | 接入底座的扩展点 |
|---|---|---|
| **能力修正** | 水生种的 `swimSpeed`、水中耐受、辫子托举等系数（按 Wiki 设定：漂浮不等于会游，不能潜水） | 能力表的物种修正 |
| **地形与物品** | 帽子四种形态；展开后的帽船是会漂浮的动态地形和容器 | 动态地形注册、容器注册、归属形态注册 |
| **需求与意图** | 想在水上生活、要回水上、出航练习（初航）、夜泊 | 需求注册 |
| **规则与演出** | 水上家庭规则、落水事件、帽船动画片段 | 后果规则注册、演出片段注册 |

### 3.2 帽子：一个物品，四种形态

| 形态 | 外观 | 物理身份 | 转换（都由技能完成） |
|---|---|---|---|
| **戴着** | 在头上 | 身体的一部分 | 摘帽：用辫子摘下，变为“托着”或直接放下 |
| **托着／叼着** | 在辫子或嘴边 | 被搬运物 | 放到水面就变“展开”；放到地上就是地上的物品 |
| **展开（帽船）** | 帽口朝上 | 浮动地形与容器 | 扶起并戴上，回到“戴着” |
| **翻覆** | 帽冠朝上 | 浮动物体，仍可推、可扶 | 用 Push 加力矩扶正，回到“展开” |

- **尺寸只有一个**：`HatScale.of(owner)` 是这顶帽子的物理尺寸，四种形态只改姿态，不改大小，从而修好“自救后帽子瞬间变大”。
- **用户裁决（Q3）**：四种形态统一一个尺寸。取一个既戴着不显得奇怪、又能当船的大小：介于普通帽 1 倍与现行船帽 1.75 倍之间，建议从约 1.4 倍起试。
  - 改模型前先出预览：成体戴着的正、侧面，以及展开后载成体加两只赤油、载成体加一只子油，三张同屏。
  - 用户确认后写入制作源登记。
  - 子油的帽子按自己的体型同比计算，初航时不再换帽。
- **归属与找回**：帽子不在头上、也不在认可位置时，主人身上的 `ResolveOwnHat` 需求一直存在。找回手段全部来自技能：游过去、推回来、扶正、托起戴上、请亲油代取。

### 3.3 帽船：会漂的小陆地

| 方面 | 设计 |
|---|---|
| **形状** | 两份数据，都由帽模型离线导出：（1）**帽面高度场**：帽局部坐标下的 2.5D 网格（约 1/4 格分辨率），每格记录可站高度，覆盖帽檐、台阶、帽井、帽底；帽壁就是高度的陡升。（2）**帽外凸包**：几个盒子，只用于水中身体和其他实体的碰撞。站在帽内的身体只和高度场打交道：落脚高度取足迹下的最高值；高差超过 `stepUp` 就是墙，需要 Hop。高度场与帽子朝向无关，查询是常数时间，不需要凹形实体碰撞 |
| **站立与行走** | 帽内就是高低不同的地面，Walk/Hop 与陆地相同，帽内导航面由形状生成 |
| **上下船** | 没有专门流程：走到边，蹦上去或蹦下来；在水里就游到边，扒上去 |
| **随船移动** | 平台携带：支撑面在帽上的身体随帽子平移和转动 |
| **倾斜** | 坡度力作用于帽内身体，`grip` 抵抗；抓不住就滑动或跌出，跌出就真实落水 |
| **浮力** | 按排水量；翻覆时帽内的空气让空帽浮起；进水量决定下沉。任何形态都不会把速度清零 |
| **被推** | 可被油库里和实体按质量比推动，可以被推上岸 |
| **与水中身体** | 任何形态下都与水中身体碰撞并分离，不会重叠 |
| **翻覆** | 由真实外因决定：摇晃、撞击、超载加水流、浸水；乘员是被物理甩出去的，不是被脚本放出去的 |
| **容量** | 由几何与浮力自然决定：挤不进就进不去，太重就吃水深、更容易翻 |
| **偏好位置** | 船长位、育儿窝、如厕处、储粮侧窝是“地名”，只作为 `GetTo` 的目标和朝向提示 |
| **储粮** | 粮袋是帽腔里的真实物体，占空间，也参与重量和重心；放置位置按现有造型规则 |

### 3.4 水上生活：由需求驱动，取代船长阶段机

- 现有 `VoyageController` 有 13 个阶段（ASHORE、PREPARE、MUSTER、MOOR、LOAD、EMBARK、AFLOAT、RETURN、DOCK、DISEMBARK、STOW 等）。这是固定流程，每个阶段都有自己的门槛，是“死板”的主要来源之一。
- DLC 改为**需求加意图**：

| 需求或意图 | 产生条件 | 拆成的技能组合 |
|---|---|---|
| **想在水上生活** | 水生种的常驻偏好；下雨、夜晚、缺粮时降低 | 备齐木棍和粮（Fetch）→ 到岸边（GetTo）→ 摘帽放到水面（展开）→ 带孩子上船（GetTo 或 Carry）→ 自己上船 |
| **需要上岸** | 缺粮且水上找不到食物、要繁殖、要找木棍、天气恶劣 | 划向可达岸边（Paddle）→ 孩子先上岸（各自 GetTo 或被 Carry）→ 自己上岸 → 收帽（托起戴上） |
| **夜泊** | 夜里或雨雪 | 找背风岸凹（规划）→ 划过去并卡住（Paddle + Hold）→ 孩子进帽腔（GetTo 育儿窝）→ 盖住孩子睡觉 |
| **采食与补给** | 饥饿、储粮不足（冬季提高） | 捞漂浮食物（Paddle + Grab），或上岸采集 |
| **照料孩子** | 孩子饥饿、不安、落水 | 帽内 Walk 到孩子身边，喂食或安抚；落水则走救援（3.6 节） |

- “船长”不再是一个模式，**谁在划船谁就是船长**。原来阶段机里的规则（先载幼体、船长最后上船）**不做硬性规定**（用户裁决 Q4），由护幼欲望等驱动自然产生；无桨只能漂是物理事实（没有划桨物就没有推力）。
- 原阶段机中有业务意义的约束全部保留，改由需求或代价表达：
  - 雨天暂停出航；
  - 生殖只在岸上；
  - 水生个体只与水生个体配对；
  - 岸上活动增加体力负担。

### 3.5 家庭、生产与初航

| 内容 | 设计 |
|---|---|
| **在帽船上生产** | 底座的 `BirthExit`（出口朝向）对帽腔容器同样适用：在能接住的落点中选转身最小的朝向；落水是真实后果 |
| **新生儿安置** | 新生儿就是落在帽腔里的身体，不分配座位；挤不下就会滚到别处，甚至落水 |
| **送一只赤油到父船** | `Fetch(赤油 → 父船帽腔)`：Grab 加 Carry；够不到时规划器让两船靠近 |
| **喂食与安抚** | 帽内 Walk 到孩子身边接触，与陆地共用照料逻辑 |
| **初航（学习）** | 一项学习需求：子油达到体型和能力门槛后，与亲船一同出航练习。练习由“摘帽放船 → 上船 → 划一段 → 返回 → 收帽”这些真实技能组成，完成才记为学会 |
| **子油搭乘亲船** | 子油只是站在亲船这块地上，自己的帽子仍戴在头上 |

### 3.6 落水、救援、翻覆

| 事件 | 设计 |
|---|---|
| **落水** | 身体实际入水时产生落水事件（沿用 `WaterIncidents` 的事件记录与一次性友善选择），本人立即得到“上船或上岸”的意图 |
| **自救** | `GetTo(帽腔或岸)`：Swim → Climb；够不到边沿就换边沿；帽子翻了就先 `Right`；体力耗尽就漂向岸，仍可能溺亡。打滑上限保留，打滑与否由抓握和物理决定 |
| **他救** | 救助者得到 `Fetch(落水者 → 安全处)`；手段有：帽内挪位后 Reach，划船转向或靠近，下水推，托起 |
| **翻覆后的帽子** | 浮在水面，可被推、被扶；主人的 `ResolveOwnHat` 负责收回 |
| **水伤** | 沿用现有数值（普通个体每 20 tick、水生种每 60 tick 扣 1 点） |
| **非亲救助** | 沿用一次性友善选择，结果记在事件上 |

### 3.7 与其他系统的交界

| 交界 | 设计 |
|---|---|
| **捕食者** | 捕食者落地同样走规划：没有干燥落点就继续飞向岸边，不会掉进水里（底座能力，陆地模块受益） |
| **玩家交互** | 帽船容器与帽上身体用同一套命中解析：点到身体就交给身体，点到帽子才交给帽子 |
| **天气与温度** | 作为需求的输入，不作为门槛 |
| **聚落与公仓** | 水边聚落把帽船当作可停泊的地形，公仓存取走 Fetch |

### 4.2 能力展厅（一级）展台

| 展台 | 对比 | 通过标准 |
|---|---|---|
| 台阶 | 赤油、子油、成体分别面对 0.1、0.25、0.5、1.0 格高差 | 跳得上的用低弧跳；跳不上的不跳，绕路或放弃 |
| 跨缝 | 0.3、0.6、1.0 格宽的缝 | 先走到边缘再跳 |
| 帽内行走 | 平稳、倾斜、剧烈晃动的帽船 | 站得稳的不动；抓不住的滑动或跌出；不穿帽壁 |
| 岸到帽船 | 帽船离岸 0.3、0.8、1.5 格 | 近的蹦上去；远的等船靠近或游过去 |
| 水中扒檐 | 浮着、翻覆、半沉的帽 | 扒正常帽能爬上；翻覆帽先扶正；不重叠 |
| 推帽船 | 空帽、载重帽 | 能被顶动，载重越大越难推 |
| 叼与托 | 赤油、子油、木棍、食物 | 太重就搬不动；放下后落在实际位置 |
| 入窝 | 宠物窝、野生窝、接生帽 | 只有身体落在内底面才算到；站在边沿会继续往里走 |

### 4.3 组合展厅（二级）

| 组合台 | 看点 |
|---|---|
| 够不到的赤油 | 亲油先在帽内挪位，仍不够就转船或划近，再用辫子托起 |
| 太远的岸 | 子油不硬跳：等船靠近，或请亲油托 |
| 翻覆的帽船 | 主人游过去扶正再上船；扶不动就推到浅处 |
| 被挡住的窝 | 绕到另一侧进窝 |

- 每个里程碑结束时，结构守卫的未迁移清单必须变短。

### 5.3 每个里程碑的完成定义

1. 交付表中的内容全部接入；“删除”栏中的旧代码确实删掉，而不是保留不用。
2. 结构守卫的未迁移清单比上一里程碑短。
3. 对应展厅或场景已更新，待办条目写明观察点，状态为**已接入待试玩**。
4. 用户试玩认可后才算完成。

## 第七部分　治理：不再回到特判

1. **结构守卫**：在 `scripts/check_architecture.py` 增加规则，禁止物理层外写位置、速度、朝向和骑乘。未迁移清单只减不增。
2. **评审红线**，以下改动一律退回：
   - 为某个场景增加的条件分支；
   - 行为代码里出现跳跃高度、时长、曲线；
   - 新的拒绝原因却没有对应手段；
   - “失败后原样重试”。
3. **问题分诊顺序**：先在能力展厅复现。能复现就修技能或能力；不能复现再看规划；最后才看行为。
4. **待办写法**：每条问题注明归属层（能力、技能、规划、行为、演出），修复只能落在该层。
5. **冻结**：M0 起，水生模块只接受按本设计的重构提交；补丁式修复只在影响试玩安全（崩溃、存档损坏）时允许。

## 第八部分　风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 帽内碰撞实现困难 | M4 延期 | 帽内不做凹形实体碰撞，改用帽面高度场（3.3），与陆地地形同一种处理；只有帽外用凸包与水中身体碰撞。大倾角时由坡度力和 `grip` 判定滑落。先做离线预览和单独展台 |
| 平台携带抖动 | 观感差 | 固定顺序：帽子移动 → 携带 → 身体移动；客户端插值同序 |
| 去掉阶段机后行为变得不可预测 | 难排查 | `[intent]` `[plan]` 日志与读数命令；组合展厅专门验证手段选择 |
| 物理导致更多意外落水 | 玩法偏难 | 由能力系数调整；先展厅定稿手感，再进行为 |
| 迁移期新旧并存 | 冲突 | 守卫白名单标出未迁移调用；同一时间只一条线改核心文件 |
| 工作量大 | 周期长 | 按里程碑交付，每个里程碑都有用户可见的改善（M2 起陆地问题先好） |

## 第十部分　与现行规则的关系

保留不变的设定与数值：
- 水伤频率；
- 漂浮不等于会游、不能潜水；
- 生殖只在岸上，水生个体只与水生个体配对；
- 一次性友善选择；
- 翻覆的真实外因；
- 储粮位置的造型规则；
- 雨天暂停出航；
- 岸上活动增加体力负担；
- 帽子尺寸由 Q3 裁决改为统一尺寸：幼体帽按自身体型同比，初航不换帽。

改变实现方式但结果等价的部分：座位改为偏好点、阶段机改为需求、转移票据改为技能。这些在 M4、M7 合入时改写 [水生魔理沙](AQUATIC_MARISA_IMPLEMENTATION.md) 的对应段落。
