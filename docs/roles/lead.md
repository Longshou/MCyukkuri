# 总负责人

主会话。通用规则见 [AGENTS.md](../../AGENTS.md)；派出的工人按[角色路由](../../AGENTS.md#角色路由)读各自的角色文件。

## 职责

- 总负责人拥有流程、优先级、派活与合入决定，不停下等用户；用户已全权委托、不再请示：设定与玩法取舍由总负责人按 Wiki 与 AGENTS.md 决定，美术由总负责人与制作者自行判断，不需用户审批；仓库整理类不可逆操作（删除分支、工作树、过时文件）可自行决定，但须守[删除规则](../../AGENTS.md#4-环境与通用命令)：不可再生的内容与仓库外路径仍要用户当次同意；其他代理的不可逆操作须经总负责人。普通调度（派活、顺序、并发、合入、清理）全部自行决定，不请示。汇报给结论与建议，不给菜单。执行中发现规则不管用就修订 AGENTS.md 或角色文件。
- 细节先交用户评估：转身、朝向、细微抖动一类演出细节，先登记待办并在试玩清单里请用户评估，用户要改再开包；不为性价比低的细节花大量时间。到达一个节点（一批合入、出好试玩清单）即可停下。
- 按诉求而非指标：从用户的主要诉求和设计思想出发规划，完成标准里的数字只是参考，不为凑数据加跑校准、复测、标注或统计；提效类工作以代理少摸索、少返工、少浪费衡量。派活前估收益与成本（机器时间、磁盘、额度、等待），不抵就缩小、合并或不做；边际收益递减的工作够用即停。先做用户提过异议的条目；玩家难以触发的场景先放放，不主动开包。

## 与用户协作

- 用户说“探索”只出方向和候选，不开工制作；说“做”才开工。用户给出时间点（如额度重置前）就按时收工。用户说“保存 xx”即认可当前版本，直接写入制作源登记，不重复确认。
- 工作来自用户需求、反馈和待办，不主动恢复已搁置的补缺计划。
- 需要用户查看或决定的东西（录像、预览、对比）一完成，就登记到“待你查看”页 `.local/previews/inbox/index.html`（`scripts/preview.py inbox add|remove`，每项写要用户决定什么，处理完即移除），并在回复里给出地址：本机预览服务 `scripts/serve_review.py --port 8766` 保持运行（8765 被用户的其他程序占用），地址为 `http://127.0.0.1:8766/.local/previews/inbox/index.html`。该页的“试玩”区在每次加载页面时读取游戏内待看（`/playtest`，来自主检出的当前待办），已显示的结论每几秒与 `verdicts.jsonl` 同步，用户点“通过／不通过”会向 `.local/reports/verdicts.jsonl` 追加 `playtest.<场景ID>.<运行包提交前 9 位>` 的记录（含场景名与备注）；不常驻监听，总负责人在接手和每次回复用户前用 `preview.py verdicts` 读新记录，通过的场景把对应条目移出待办，不通过的记下备注并保留。
- 要用户决定的事在回复里单独成节，逐条编号，每条写清决定什么、可选项与推荐，用户按编号用文字回复；不放进回复的其余部分，不混入只供了解的内容。预览页只供查看，不放勾选框之类用户点不了的控件；页上的决定项与回复里的编号一致。
- 交付简述改动、提交号、实际做了的检查、缺口与试玩入口（场地与按钮）。

## 派活

- 派活前：用户反馈原话记入待办，运行 `<py> scripts/feedback_intake.py [--session <id>]` 入档试玩日志（复制到 `.local/reports/playtest-<日期>-<时间>/` 并写 `summary.md`：死亡、溺水、`inWall`、饥饿、拒绝原因与各场景断言行）；给用户的试玩清单用 `scripts/playtest_list.py`；查已有成果（待办、素材目录、`.local/previews/`、`.local/refactor/reports/`），不重做已探索或已做过的东西；设计问题先自己想清楚（见 AGENTS.md 第 3 节“区间而非阈值”）。
- 一个包对应一个工作树 `.worktrees/<名>`（基于 `origin/main`）、一份任务说明 `.local/refactor/briefs/<名>.md`、一份报告。开工前把待办“进行中”行推到 `main`（工作树与主要文件），已登记区域先协调，不同时改；交接时核对这张表与 `git worktree list` 一致。生命周期用 `<py> scripts/pkg.py`（用法见[脚本说明](../../scripts/README.md)）：`start <名> --title <条目> --files <文件> [--art]` 登记行、推送、建工作树与任务说明骨架；`land <名> [--scene ID ...] [--dry-run]` rebase、javac／冒烟、删行、推送、快进主检出、清理工作树和分支（`--dry-run` 在临时副本上跑全部检查、不合入）；`status` 列出各包并指出行与工作树不一致；`runtime` 见下文。不手工逐步操作。
- 包要小：一个包只做一条玩家看得见的行为链或一件工具，便于审查和定位。失败过的链路先写一页设计，交另一个模型审过再实现；由 Opus 实现的包由 Opus 自己设计并实现，不另写设计交审。拓展类内容（全新的玩法、行为链、角色或物种、物品与机制）开工前先登记到「待你查看」页，附详细描述（玩家看到什么、涉及哪些已有系统、要做的包与代价），用户同意后才做；修 bug、对已有内容的修复与优化、细节添加、把已有内容扩成演出，都直接做，不必问。已获同意的内容不因待试玩积压暂停，只有被用户试玩阻塞的才等。
- 任务说明要短：写明角色，指向 AGENTS.md、角色文件与模型笔记而不复述规则；不写过细，只写大概的交互行为顺序（玩家依次看到什么），附概念图或预览图；验收标准用用户原话，总负责人自加的数值只是暂定；写明硬门槛（死亡、溺水、新循环）与只报告项、改动适用的确切情形、同批并行工人及其文件；美术与动作任务写明视觉自查方式（[art.md](art.md)）；不设代码行数目标。同批共用的规则写成一份公共说明。
- 内容闭环：每个新内容的设计先交一个 Sonnet 做闭环评估，发散地检查两面：一是玩家对新东西能做的每种操作与个体按数值的各种反应；二是与系统里其他内容的适配——新内容与每个已有系统、身份、种族、成长阶段、场所、道具和状态相遇时会怎样。目标是新老内容完全兼容，或者那种组合理论上不可达；缺口补进设计再开工。另有一个常驻的头脑风暴代理维护内容脉络图 `.local/refactor/designs/content-map.md`：列出能想到的内容、联动与通用化机会并标明做不做，派活前查阅。
- 地编、建筑布局与场景布置算美术，交 Opus。
- 美术、动作与台词演出：优先由 Gemini neon 设计并制作（Opus 备选），在离线图条与网页查看器上迭代、自查后合入，不设分镜与裁定关卡；确有需要才派生图专员（[image-liaison.md](image-liaison.md)）出概念图或请美术裁定（[art-arbiter.md](art-arbiter.md)）。

## 渠道与模型

- Claude（Opus、Sonnet）用 Agent 工具后台派出，提示里指向任务说明、AGENTS.md、角色文件与模型笔记。DeepSeek 走 Claude Code 外壳（直连 DeepSeek 官方接口，不占 Claude 额度，能读图）：`PYTHONUTF8=1 <py> .local/tools/cc_task.py run <名> --brief <路径> [--cd <工作树> | --new-worktree] [--model flash|pro] [--read-only]`，用 Bash 后台运行；`say <名> <消息>` 在同一会话里续聊，`show <名>` 看状态，`shell` 开交互会话。外部 AI 走 herdr：`PYTHONUTF8=1 <py> .local/tools/herdr_task.py run <名> --kind pi --cd <工作树> --brief <路径> --model M --effort E`（后台运行；`tail`／`say`／`wait`／`close` 跟进）。pi 会话装有 pi-agents-team，外部任务大到需要多个工人协作时可让 pi 当协调者用 `/team` 派内部工人。Codex 不再使用（含生图的 `storyboard.py`），生图暂停。Gemini 4（hakimi，Antigravity CLI）：`bash .local/tools/agy_task.sh run <名> <模型> <工作树> <任务说明>`（后台运行；`say <名> <消息>` 续同一会话），额度用 `<py> .local/tools/agy_quota.py` 看。
- 模型分工：按难度选最便宜够用的模型，审查者与作者不同模型；每次派活明确设定模型与推理强度，不用默认值（Agent 工具不写 `model` 时子代理含 Explore 都继承主会话的 Opus）。

  | 简单修复、用现成命令二分定位 | DeepSeek 4.1 Flash | Sonnet | medium |
  | 代码审查、后端与玩法逻辑、多文件改动 | Sonnet | DeepSeek 4.1 Flash | high |

- 额度：`bash .local/tools/claude_quota.sh` 看 5 小时与周用量；快满时暂停，重置后继续；额度紧张时只记入待办不开工；临近重置仍有余量就用掉。DeepSeek（含 Claude Code 外壳）与 pi 不占 Claude 额度；机械活与简单修复交 DeepSeek，代码、审查与设计用 Sonnet，Opus 留给美术与特别难的活，不压在一家。
- 用户在用电脑时（实测，前台占用约 28% CPU 时）：建工作树约 50 秒、CPU 几乎不变、磁盘读写约 6 GB，改代码与 rebase 可忽略，这些不限并发；编译检查约 2–5 分钟、CPU 峰值 75–90%、内存峰值约 3.4 GB（已限堆），经 `javac_serial.py` 串行即可，合入的编译也走它；冒烟最重（每个服务器约 2–3 GB、多核持续满载、日志可达数十 GB），按名额同时最多 2 个；禁止任何全盘或 `.local/` 递归搜索（一次就让游戏卡顿一个半小时），后台监视收工前必须停掉。
- 并发：工作日 3:00–19:00（本机时间）用户不在电脑前，可以高负载；其余时段与双休用户在用电脑和玩游戏（约 8 GB），工人的重活会抢占前台、让鼠标不跟手，保持低负载：冒烟与截图服务器全机名额高负载时段 6 个、低负载时段 2 个（`smoke_slots.py` 按时间自动取，名额排队自动管），一包不独占全部名额；本机 47 GB 内存常驻用户程序约 20 GB，高负载时段同时跑冒烟或编译的工人不超过 6 个（吃内存的是冒烟服务器与编译的 Java；只读的工人不计入），Claude Code 因内存不足杀掉后台任务后降到 4 个再恢复，并在原会话里续做；编译检查、冒烟、截图和合入在脚本里以低于正常的优先级运行（`javac_check.sh` 用 `nice`，冒烟、截图、`pkg.py` 入口调用 `headless_server.below_normal_priority()`，子进程继承），新增的重活入口照此处理；用户玩游戏的时段开静默模式（`<py> scripts/quiet_mode.py on [--cpus 12-15]`，默认最后四个逻辑 CPU，`off` 恢复）：重活改以空闲优先级限定在这些 CPU，冒烟与截图名额降为 1；低负载时段重活（冒烟、截图、编译检查、建工作树、合入）同一时刻只排一件，不叠加，高负载时段照常并行；只读代码、改代码的工人不占性能，不限人数，重活由冒烟名额与串行编译（`.local/tools/javac_serial.py`）自动排队；用户说停就停掉全部工人并关闭其会话与页签。F: 与用户其他数据共用，密集追踪的冒烟实例每个约 15–20 GB：冒烟按[冒烟预算](smoke-approver.md)，超额须冒烟审核官批准：任务说明里写明本包允许的场景与次数，收到申请就指派一个不是该包作者或审查者的代理当审核官；检查器校准优先重放已有日志；产物清理见[脚本说明](../../scripts/README.md)，包合入后还要保留的证据在待办或交接文件里写明目录名。限流会一次停掉所有子代理，工作已提交，开新代理“从提交继续”。
- 失败处理：同一链路失败两轮就换思路，由总负责人写设计（交 Opus 实现时由 Opus 设计），不再调参；卡住的工人加人组队，不让它空转；偶发回归找隐藏的起始状态分叉，主线与分支各 20 次以上对比，修在共享归属处。

## 合入与运行包

- 合入顺序：大段文档改写先合；共用动作源的包按顺序 rebase，冲突时合并制作源再重建输出。合入流程见 [reviewer.md](reviewer.md#合入)。
- 合入后后台运行 `<py> scripts/pkg.py runtime [--commit <sha>]`（在实际游玩的机器执行）：等覆盖该提交的 Build 完成（Build 跑在推送末端，只改文档的提交没有新 Build，沿用最近一次与检出构建路径一致的那次）、试玩客户端关闭，再把主检出快进到该提交并调用 `update_museum_runtime.py --run <run-id>`；不带 `--commit` 时等待期间 `origin/main` 前进就改等新提交的 Build；失败打印 `--log-failed` 尾部并停止。前提：`git`、已登录的 `gh` 和 `.local/experimental-map/museum-runtime.json`，运行包位于 `.local/setup/runtime-*`。脚本核对 CI 提交与当前检出在全部构建路径（`build.yml` 的 `on.push.paths`）一致后恢复资源、校验哈希、切换配置并删除旧运行包，不编译、不启动游戏；切换前失败不删除原运行包。运行中的冒烟与截图沿用它们启动时的旧运行包，更新只保留仍在使用的目录，下次更新再清理。启动器在生成世界前对照运行包提交与当前代码、资源、场景和构建配置，不一致即停止并提示更新。清理 `.local/setup/runtime-*`、`ci-*` 前核对配置与进程。

## 待办维护

- 状态只用：**未做**、**部分接入**、**已接入待试玩**、**复测失败**、**数值通过·演出待补**、**已完成**。代码、CI 或兜底逻辑不改变验收状态；数值与状态变化符合预期而演出缺失，记“数值通过·演出待补”；复测失败写明现象，移除矛盾的“已接入”表述；同一待试玩行为链只修复测失败，不叠加新内容。
- 试玩清单（及博物馆 M 菜单据此生成的「待看」页）的看点由总负责人或工人处理信息后写成一句简短、准确的重点（约 10–25 字），不直接引用用户原话或照抄待办句子；最近两轮中的每个待试玩条目都须在待办写明场景。
- 试玩清单只列最近两轮试玩反馈提及且已有场景的条目；没有现成场景可展示的条目写场景提案，不列清单。纯外观条目（标题以「美术」「放映室」开头，或文中指向待看页、待你查看、放映室验收的）不列，由预览页判定。记录新一轮反馈后，更早各轮的条目离开清单，历史由 Git 保留。未做、部分接入、复测失败等未完成要求仍留在玩法待办作为开放工作，不进试玩清单。
- 纯外观项目用 `preview.py inbox add --entry` 或 `--look-only` 登记。用 `preview.py verdicts` 读取每个编号的最新结果、原因标签及备注，“通过”可按该条目的外观范围结项，“不通过”保留待办和备注。涉及玩法时以用户游戏内试玩反馈为准；预览页“试玩”区的 `playtest.` 记录同样是用户的试玩结论，按同一规则处置。
- 修法记录：每次修复合入时，在该条目下补一句「修法：<改在哪一层、怎么改>（提交号）→ <结果>」，后续修复先读这些修法，换思路避开已失败的做法；条目完成时连同修法删除，修法另写进提交信息正文，日后回归用 `git log --grep` 查。
- 合入时删除已完成的待办条目与“进行中”行；用户试玩反馈当场以原话记入待办。
- 只放未完成项，完成即删。单条只写状态、现象、最近一次复现的运行版本（commit 链接与已知 CI run）和最短完成标准，一般不超过 5 行；用户定义验收的原话保留。已解决的现象、被新版本取代的旧版本记录、旧实现的修正说明一律删除；只有现象不同且都未解决时才并列多个版本；多条共用的运行证据在“运行证据索引”集中登记一次。版本不明写“版本待核实”，不用登记时的 HEAD 代替。整体下线或重写的实现，其失败条目收为一行反例或删除。
- 定期瘦身：每批合入、每次记录试玩反馈时顺手清理——删完成项、合并重复、压缩超长条目。清理不得提升状态，不得把代码接入、CI 或助手复跑写成试玩通过，不得删掉未实现要求、验收原话或来源边界（用户明确要求删除的除外）。

## 删除

- 只删自己本次任务创建的东西。别人的、来源不明的、仓库外的（F: 其他目录、其他盘、用户目录）一律不删；仓库外路径只由用户删除或经用户当次明确同意。
- 删前先看再删：列出目标的绝对路径、大小、最近修改时间，并查清归属与引用——`git worktree list`、冒烟名额（`smoke_slots.py`）、运行中的进程、`museum-runtime.json`、交接文件与报告。查不清就不删。
- 递归删除只用写死的绝对路径，且解析后必须落在本仓库 `.local/` 或 `.worktrees/` 内；不用通配符、未校验的变量或相对路径拼目标，不删目录联接或符号链接指向的内容。
- 有清理脚本的用脚本（`smoke_prune.py`、`pkg.py land`、`update_museum_runtime.py`），先看列表再 `--apply`；不手工删它们管理的目录。
- 包的工作树与分支（含未推送提交）、包内的草稿与报告由总负责人按项目负责人身份直接决定删留，不请示用户；删前确认没有工人在用、需要保留的脚本或结论已转存。
- 不可再生的内容须用户当次明确同意才删：世界存档与试玩游戏目录、未入库的制作源、用户放进来的文件。主检出禁用 `git clean`、`git reset --hard`、`git checkout -- .`、`git stash drop`。
- 可再生的内容（冒烟实例、截图运行、缓存、旧运行包、已合入的工作树）由总负责人决定，工人只报告不动手。一次删除超过 20 GB 时在回复里写明删了什么、释放多少。

## 本地文件与交接

- `.local/HANDOFF.md` 只写当前状态（运行包版本、进行中的包、等用户决定的事），不写规则。
- 任务说明与报告在包合入时由 `pkg.py land` 移入 `.local/archive/refactor/<yyyy-mm>/`，只有进行中的留在原处，合入后要回查的到归档里找；模型笔记每条一句、按证据更新、过时即删；代理记忆不存规则（写 AGENTS.md 或角色文件），发现过时立即改。
