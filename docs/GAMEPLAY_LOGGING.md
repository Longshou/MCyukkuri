# 玩法日志

状态：**已接入待试玩**。开发约束见 [AGENTS.md 的日志留痕](../AGENTS.md#日志留痕)；运行包、日志位置与按时间查找方法见[开发指南](DEVELOPMENT.md)。日志用于还原实际发生的事件，不代替用户在试玩场的确认。

## 后续功能的规则

- 新增或修改玩法时，一并留下关键事件：明确的玩家操作，行为链开始、重要阶段、完成和中断，实际伤病、亲缘、归属及物资变化。发生过的尝试被拒绝，要记录已有判定中的原因或阻塞条件。
- 在拥有业务状态的组件里记录结果。不要为日志再调用治疗、寻路、扣料、抽签或其他会推进玩法的函数；概率记录复用本次结果。开始接近、开始吃饭、实际吞咽必须区分，不能把开始写成完成。
- 重要事件默认 `INFO`，服务端记录一次。客户端渲染和同步不重复记同一事件。已有 `[headwear]`、`[mind]` 等日志继续保留，不再平行重复。
- 新日志用 `status/GameplayLog`：`event(entity, category, message, values...)` 自动附品种／实体类型、`#id`、UUID、游戏 tick、维度和位置。跨重载追同一实体用 UUID；实体数字 ID 只在本次运行内有效。关联目标、brood、票据、聚落或物资要在正文保留标识。
- 没有存活实体的交易用 `world(ServerLevel, ...)`，正文必须给出事务／地块标识。拒绝和等待用 `limited` / `worldLimited`，key 由稳定的事件与原因组成，不能把当前时间、坐标小数或剩余冷却塞进 key。
- 通常同实体、同原因 200 tick 至多一条；明确玩家操作的连点用 20 tick，追击／俯冲切换用 100 tick，部分无草场重试用 1200 tick。按模拟 tick 计时，20 TPS 下分别约为 10 秒、1 秒、5 秒、60 秒。下一次同 key 输出带 `suppressed=N`，表示中间省略的调用次数；没有下一次调用就不额外补一条。
- 限频缓存只在运行期存在，不写 NBT。统一入口每实体／世界最多 64 个 key，弱引用所属实体／世界；达到容量会清空该桶，因此不会保证大量不同 key 并发时仍严格保持原间隔。
- 文本只留排查所需字段。记录实际数量、生命小数、前后状态；不输出完整 NBT、背包或寻路节点。新增系统要同步本页覆盖范围和有意省略项。

## 橙汁与疤痕排查

在试玩场陆 49，先清空本场地，再按原场景操作。以正在运行包的 commit、CI run 和测试时间定位日志，不用当前源码 HEAD 代替。搜索同一实体的 `[body]`：

1. 受伤后应看到 `wound placed/deepened ... on ...`，生命损失保留小数；封顶或无新增变化会写 `wound unchanged`。
2. 橙汁成功应看到 `orange juice cleared N wound(s)`、治疗后生命 `X/Y` 和治疗前生命，随后玩家操作日志给出实际物品数量前后值。没有适用伤病或正在惊慌／水中／着火／濒死等会记录 `treatment refused`，不会消费一剂。
3. 自然愈合或舔舐闭合最后一级时，`scar formed/not formed` 给出伤型、峰值、概率和本次抽签；疤痕已满则写容量原因。橙汁直接清除活动伤口不经过成疤抽签。
4. 面粉糊应看到 `flour paste cleared N scar(s)`，包括旧伤口列表中的疤痕计数；活动伤口和生命读数不因面粉糊变化。

其他链路在原有场景复测即可：护子看捕食目标 UUID 是否转到亲油，妖梦战斗看双方每次真实受击与停止条件；接生／喂食看 brood、新生儿、取粮→交餐→吞咽；水生救援看阶段、滑落原因和登船。没有对应日志时，结合现场阶段读数与 `/yukkuri status` 判断是否尚未进入该边界，不能仅凭“没有成功日志”断定没有执行。

| `voyage`、返帽与救援场景 | `[voyage]` 串起初航阶段和退出原因；`lesson completed` 只在完成航程、返回亲油帽且取回自帽后出现。`[boarding]` 对照实际登船乘员，`[cradle]` 对照抱持／放下及失败后释放；`[water]` 对照 `water.distress` 的落水阶段、疲劳、救援引导。普通落水救子看 `[aquatic] braid rescue decision` 的亲代／帽／幼体、概率和本次接受结果，物理重试不重复抽签；翻船救子看 `attempts/window` 及交还自救的事件。结合 `water.self_rescue`、帽船乘员和现场阶段读数，区分仍在接近、登船失败、抱持中断和已登船。 |
| `cargo_full`、`cargo_load`、`cargo_stow`、`cargo_rescue`、`capsize_siblings` | `[cargo]` 对照实船库存：挪到帽缘只改变 `aside`，不增加总粮；喂食取粮后总量减一，实际营养仍看 `[meal]`；弃粮／散落以 `spawned` 数量核对地上实物，桨是否保留单独记录。`[family-alarm]` 用亲油 UUID 与 `event` 开始 tick 串起召回，等待因超时／对象不可用而结束不表示孩子死亡或已返船。 |
| 水上起点 `cargo_load`、`shore` 与没收 `hat_custody` | 场景分别记录初态准备完成与失败回滚，初态完成不表示被测行为完成。造船的 `hull collision` 保留本次实际拒绝类别 `block/entity/world_border`、船体包围盒和碰撞检查上下文 UUID；方块给首个阻挡形状的边界，实体给碰撞形状数量，不据此猜具体实体或方块。没收记录真实靠岸、乘员交接开始／结束／中断、实际剩余乘员、拒绝原因及帽子进入主背包的槽位；只有乘员已实际离船后才结算。`water.cargo` 可在帽主离船后继续读取其原帽的没收阶段、当前乘员和最近拒绝原因。日志与读数用于定位交接，不能代替用户试玩。 |

家庭链还记录实际求偶权限判定、接触开始、停止原因和受孕结果；喂食意愿补充本次抽签值，已选中饥饿子油但未找到粮源时限频记录双方营养。亲油死亡时记录携带照护粮是否成功生成掉落物。失散寻亲在实际 Goal 首 tick 记录目标／最后已知位置；普通跟随、守家、等待孩子的频繁停止不记 INFO。

`feed`、`first_toilet` 场景的会合问题可按双方 UUID 追 `[care]`：`agreement reserved` 后，`no_reachable_meeting` 表示原有选位未得到结果；`replan` 留下重选前的站位、停滞和身体接触计数；停止原因区分重试上限、孩子离开会合点、协议超时与亲子状态失效。`external_or_owner_finished` 只表示调用者清理协议，是否完成喂食／首便仍看 `[family]`、`[childhood]`、`[meal]` 与现场读数。完成标准是能区分“尚在接近、条件拒绝、重选失败、实际接触并完成”，不因新增日志改变原有行为状态。

茎生结束后的空茎实物交接用 `[family] shed stem queued/delivered` 串起母体、brood 与掉落物 UUID。`queued` 只表示已登记；`delivered existing=true` 表示找到了此前已经生成的同一物体，不重复声称新生成。身份冲突和生成被拒绝按 brood 与原因 1200 tick 限频，区块未加载或幼体尚未落定不逐次记录。

低频生命周期可在原有试玩入口核对：`factory_wear` 的 `[factory] parent cycle recorded`、`parent retired` 和 `replacement pair assigned` 对照真实组号、服役次数及用途；`agitation_relief` 对照躁动阶段和剩余期，读档初始阶段不当作新发生事件。宠物请求看请求图标／状态与 `[request]` 的类别、主人、过期时主人是否在附近；`satisfied` 表示请求条件满足（食物请求也可能由附近食盆有粮满足），不替代 `[meal]` 的真实吞咽。娱乐设施日志的 `completed` 与现场是否走完整条设施路线对应，纯动作播放不计作设施使用。

路线日志只表示已选中可执行路线，实际运行 Goal 仍以现场读数为准；限频见[采样规则](#采样限频与证据边界)。

## 水上生态交接

- `[aquatic] shore work requested/released` 记录已提出的靠岸工作与保留释放，不能当作已经上岸或完成课程。`hull grounded/refloated` 只在实际失去／恢复水面支撑时记录；不逐 tick 转储流体采样。
- `[temperature] water refuge selected` 记录选中的可达水面及体感；`no safe water refuge` 按实体限频 400 tick。冬季原有 `[winter]` 记录实际开始／结束，睡眠由 `[sleep]` 记录。
- `[forage] shore plant harvested`、`provisions received`、`returned to bank` 分别表示实际植物消耗、随身粮转移和回岸储粮；岸上采集、上缴继续看原有 `[forage]`、`Levy` 记录。`[cargo]` 腐坏事件给出实际库存前后值和间隔，不记录每 tick 计时。
- 试玩 `water_life`、`water_winter` 对照 `water.cargo` 的 `shoreWork`、库存目标、觅食阶段和温度活动，以及实船 `Cargo.DecayTicks`。空库存不等于附近没有食源；未看到靠岸日志时先看实际 Goal、照料和警报是否占用船只。

- `[daily]`、`[social]` 区分邀请保留、靠岸等待、落岸重查、真实接触与最终完成；读 `behavior.daily_session`、`behavior.group_session` 的 `shorePending/contact/elapsed`。未落岸的邀请不会增加接触奖励。
- `[headwear] received/transferred` 记录完整饰品真实换主；`foreign shard used` 记录逐片材料增加。物品仅在服务器接受后消耗，拒绝不写成归还成功。
- `[settlement]` 与公仓账本分别记录水上家庭配额、靠岸取粮和实际搬走数量；一顶帽船的库存按船 UUID 计一次，不能把家庭人数乘到同一库存上。水路迁居的路段获准不等于到达与地址提交。
- `[aquatic] orphan refuge decision/reserved/boarded/released` 分别表示一次真实意愿抽取、席位保留、实际登船与落岸释放；`[cradle]` 给出跨帽搬运阶段、阻塞与真实落点。意愿未通过或路径不可达不改亲缘、不直接搬移实体。

- `[pet-walk]` 记录牵引靠岸请求、真实挂绳和取消原因；同一 `[pet-walk]` 前缀记录居民靠岸请求与取消，漂流不记散步收益。`[shop]` 的 `shore_pending` 不代表交易，`debited_after_landing` 与原 `committed` 才对应费用或归属变化，取消日志记录零扣款／零付款。
- 课程与考试沿用原开始、任务、结果日志；靠岸失败不伪造开课或考试结果。工厂只在原真实工序交接时记完成。
- 献身、遗体与食腐沿用 `[offering]`、`[cannibal]`、`[remains]` 的实际阶段与物资变化；水路寻近和嘴距采样不逐次 INFO。无咬食日志时结合实际嘴距、视线、库存和 Goal 判断，不能把已接近等同于已吃到。

## 采样、限频与证据边界

默认省略逐 tick 的移动、朝向、接触几何、动画、表情、台词、音效、代谢、微量回血和沾污；也省略普通问候、娱乐姿态、宝物凝视、幼体练习、温度采样、候选扫描、寻路节点、分片搜索等待、逐格挖掘和逐棵采草。保留真实资源、关系、技能、伤病、阶段及任务交付；明确玩家操作仍在交互入口记录结果。转接组件不重复记录领域组件的生命周期。

除上表说明的事件外，主要限频与汇总规则如下；均按模拟 tick 和稳定的主体／原因计，不用动态坐标作 key：

| 事件 | 记录节奏 |
| --- | --- |
| 岸边出航拒绝、放帽失败 | 同原因 200 tick；岸上阶段按目标阶段 100 tick |
| 迁徙拒绝、饥饿时住所／觅食阻塞、路线重启 | 1200 tick；营养跨档按目标档 200 tick |
| 日常亲昵／唱歌／运动、玩具、设施起止、缩壳、躁动阶段 | 汇总记录，1200 tick；接触中断 200 tick |
| 呕吐、玩家教学自动拒绝、审判接触变化、没收重复拒绝、牵绳拒绝 | 200 tick；呕吐复用已发生的能量变化与毒素快照 |
| 照护会合建立／重选／停止、住所宣称阶段、求偶接触和权限判定 | 200 tick；住所宣称按 claim 和目标阶段 |
| 登帽、抱持、初航、落水离散阶段及同阶段反复停止 | 200 tick；照护无粮和失散寻亲开始 1200 tick |
| 挪粮、警报阶段、救援目标切换 | 200 tick；弃粮／散落按实际转移汇总数量，不逐物品输出 |

真实拾取、采集、建船、交易与物资结算通常逐次记录，没有会丢掉交易的全局条数上限。工厂服役计数、退役与替补只在写入变更后记录；宠物请求日志不增加业务额度（每只每天至多 6 次、每主人附近至多 12 次）。遛弯逐步计程、库存空仓／满仓扫描和警报每次发声尝试不输出。

需要特别区分：

- 无可达岸候选只更新 `water.launch`；`launchCheck/checkTick` 是最近一次实际判定，可能因别的 Goal 接管而变旧。首次读到已坐船的存档只记乘员观察变化，不表示刚登船。幼体归船／死亡／独立、岸边托举和接触拒绝按真实结果记录。
- 帽船碰撞类别只在两个实际建船入口记录，候选扫描不输出。按 `CollisionGetter.noCollision` 的方块→实体→世界边界顺序取得一次结果，保持原上下文和短路顺序，不在失败后重新探测。
- 读档、库存 `load` 和警报 `load` 不补写历史事务。部分离体茎／巢的账本取消没有实体上下文，需结合调用者记录与世界读数，不为日志扫描世界找实体；有 `ServerLevel` 的出生／收容事务使用世界日志。旧日志未全部补齐 UUID。
- 只覆盖明确列出的边界，未穷尽更早的 Goal 仲裁、船上照护内部阶段或普通社交细分拒绝。没有日志不能证明行为没发生；诊断不足时补对应读数。

几何细节用 `/yukkuri aqdiag on`（关闭 `off`），状态变更细查用 `/yukkuri status trace true`（关闭 `false`）；两者默认不开启，细密日志可能较快增大文件。完整实体保存视图另由 `debug.entitySaveViews` 控制。

观察台已移除读数按钮，手工查询方法见[试玩场诊断入口](EXPERIMENTAL_MAP.md#观察台的按钮分类)。`mcylab:read/` 和报告通道只在调用时生成快照，不自动轮询，也不补造此前状态。常规排查只需场景和大概时间，按[开发指南](DEVELOPMENT.md#试玩日志与事后排查)定位运行版本与原生日志。
